# Cache-Aside 实验视频录制脚本

## 视频定位

这不是页面功能导览，而是一条完整的工程因果链：

```text
Direct 查询
→ 数据库压力随请求增长
→ 引入 Cache-Aside
→ Redis HIT 让 MySQL 离开热路径
→ 热点 Key 失效
→ 并发 MISS
→ 按 Key 回源闸门
→ Leader / Followers 分流
→ Leader 查询 MySQL 并回填 Redis
→ Followers 二检 HIT
→ 缓存恢复
→ 用指标证明保护生效
```

目标时长约 8 分 30 秒。全片只讲阶段 1「稳态性能」和阶段 2「热点击穿」；缓存穿透留给另一条视频。

> 本脚本使用 `15 MISS / 1 MySQL 回源 / 14 等待合并 / 16ms 重建 / 约 99% 命中率` 作为示例。正式录制时，只有这些数字确实来自同一轮冻结结果时才原样念；重跑数字发生变化时，必须按页面实际结果替换，不能硬凑。

## 完整逐幕脚本

### 第一幕：先展示反直觉结果

**时间：** 0:00–0:30

**画面操作**

直接停在已完成的「阶段 2：热点击穿」结果页，放大以下指标：

- 15 MISS
- 1 次 MySQL 回源
- 14 个等待合并
- 16ms 缓存重建
- 失效窗口约 99% 命中率

暂时不要滚动，也不要介绍页面按钮。

**观众此时看到什么**

缓存确实发生过失效和 MISS，但数据库只被访问了一次，整体命中率依然很高。

**旁白**

> 这一轮最值得看的不是 QPS，而是这组看起来有点矛盾的数据。热点缓存刚刚被删除，出现了 15 个并发 MISS，但真正访问 MySQL 的只有 1 个请求，另外 14 个请求被合并等待。整个缓存空窗只有 16 毫秒，所以放到一秒统计窗口里，命中率依然接近 99%。接下来我从 Direct 查询开始，把这条因果链完整演一遍。

**为什么下一步这样操作**

先用结果制造悬念，再回到 Direct 建立“没有缓存时”的基线。

**这一幕证明什么**

缓存收益不能只讲 HIT；真正体现工程能力的是 MISS 时如何保护数据库。

---

### 第二幕：固定实验变量

**时间：** 0:30–1:00

**画面操作**

回到「查询压测计划」页面：

1. 选择 `PATH A · MySQL Direct`。
2. 选择本次录制使用的固定速率。
3. 选择 `Runner 自动`。
4. 停在计划摘要，展示目标 QPS、连接配置与 30 秒时长。
5. 点击「确认计划并进入实验室」。

如需复现当前热点数据，应使用产生这组数据时相同的 QPS 和连接配置，不要临时换档。

**观众此时看到什么**

- MySQL Direct
- 目标 QPS
- 预计或锁定的 `-c`
- 固定 30 秒

**旁白**

> 我先固定业务对象、请求速率、连接策略和运行时间。两轮实验唯一改变的是读取路径：第一轮每次直接访问 MySQL，第二轮先访问 Redis。这样后面的性能差异才能归因于 Cache-Aside，而不是连接数或者流量不同。

**为什么下一步这样操作**

先建立公平对比，避免“Cached 配了更多连接所以更快”的质疑。

**这一幕证明什么**

性能实验必须控制变量，不能只拿两张结果截图硬比较。

---

### 第三幕：运行 Direct 基线

**时间：** 1:00–1:50

**画面操作**

进入实验室后点击「启动查询潮汐」，让任务完整运行 30 秒。运行时停在请求动画和实时指标区域；结束后展开最终指标与实时证据区域。

**观众此时看到什么**

- 实际 QPS
- 目标完成率
- MySQL 查询或回源持续增长
- 请求 P50 / P95 / P99
- Socket Errors / Error Rate

**旁白**

> Direct 路径的特点很直接：每一个请求都必须进入数据库，现场组装同一份材料详情。请求量上涨时，数据库工作量也近似跟着上涨。这里我不先下结论，先把实际 QPS、P95、P99 和数据库压力记下来，作为下一轮的基线。

**为什么下一步这样操作**

有了 Direct 基线，下一轮才能证明 Redis 是否真正把重复读取挡在数据库之外。

**这一幕证明什么**

Direct 的主要问题不是结果不正确，而是重复查询会持续消耗数据库资源。

---

### 第四幕：切换到 Cache-Aside

**时间：** 1:50–2:40

**画面操作**

点击「返回配置页」：

1. 只把路径改成 `PATH B · Redis Cache-Aside`。
2. 保持相同 QPS。
3. 保持相同连接策略。
4. 确认计划并进入实验室。
5. 点击「启动查询潮汐」。

镜头跟随第一次冷缓存请求，然后停在后续 Redis HIT 动画上。

**观众此时看到什么**

第一次可能出现：

```text
Redis MISS → 回源 → DTO SET Redis
```

随后大量请求变成：

```text
Go API → Redis HIT → Response
```

`KEY MUTEX / DOUBLE CHECK` 节点常驻，但 HIT 时显示 `HIT BYPASS · MISS 才进入`。

**旁白**

> Cache-Aside 不是所有请求都先加锁。正常 HIT 时，请求从 Redis 直接得到已经组装好的 DTO，回源闸门和 MySQL 都被绕过。只有第一次冷缓存 MISS，或者缓存失效时，系统才需要进入回源流程。也就是说，锁不是热路径的固定成本，它是 MISS 路径的保护措施。

**为什么下一步这样操作**

先证明 HIT 快路径，再比较两轮最终结果。

**这一幕证明什么**

Redis 的核心收益是让绝大多数重复读取不再进入 MySQL。

---

### 第五幕：比较 Direct 与 Cached

**时间：** 2:40–3:30

**画面操作**

等待 Cache-Aside 任务完整结束，展开：

- `wrk2 最终指标`
- `已完成实验与胜负对比`

把 Direct 和 Cached 两列放在同一画面。

**观众此时看到什么**

- 实际 QPS 与目标完成率
- 请求 P50 / P95 / P99
- MySQL 查询或回源差异
- Redis HIT / MISS
- Socket Errors
- Error Rate

**旁白**

> 现在才是性能结论。两轮流量条件一致，但 Cached 路径的大部分请求停在 Redis，不再重复组装数据库数据。所以我关注三件事：实际 QPS 是否更接近目标、P95 和 P99 是否下降、MySQL 工作量是否明显减少。只要这三个方向同时成立，才能说明收益不是偶然的单点数字。

**为什么下一步这样操作**

稳态 HIT 很理想，但真实系统不能假设热点 Key 永远存在。

**这一幕证明什么**

Cache-Aside 的性能收益来自数据库工作被缓存命中替代，而不是仅仅“Redis 比 MySQL 快”这句口号。

---

### 第六幕：进入热点缓存击穿实验

**时间：** 3:30–4:10

**画面操作**

点击顶部的 `阶段 2 · 热点击穿`，先展示：

- `ARC-004 热点失效与恢复`
- Redis Key 状态
- 稳定命中阶段
- `PROCESS-LOCAL · KEYED`
- `KEY MUTEX / DOUBLE CHECK`

然后点击「启动热点击穿实验」。不要寻找单独的 DEL 按钮；这一轮启动后先建立稳定状态，再由实验流程触发真实失效。

**观众此时看到什么**

失效前：

- Redis Key 存在
- 命中率稳定
- MISS 接近 0
- MySQL 回源接近 0
- Mutex 节点处于灰色 BYPASS 状态

**旁白**

> 热点击穿的前提是这个 Key 原本很热。现在请求几乎都命中 Redis，MySQL 不参与，回源闸门也处于旁路状态。接下来我会让 ARC-004 真实失效，观察这批同时到达的请求会不会一起冲进数据库。

**为什么下一步这样操作**

必须先证明它是热点 Key，后面的并发 MISS 才能称为击穿风险。

**这一幕证明什么**

缓存击穿不是普通冷启动，而是一个正在承载高流量的热点 Key 突然消失。

---

### 第七幕：热点 Key 真实失效

**时间：** 4:10–4:50

**画面操作**

当页面进入真实失效阶段时，把镜头停在：

- Redis Key 状态
- 因果阶段标记
- HIT / MISS
- MySQL 回源
- P95 / 峰值

后期可对这一帧停留 3～4 秒。

**观众此时看到什么**

画面出现 Redis Key DEL 或不存在，紧接着并发 MISS 增长、回源闸门被点亮，峰值延迟出现短暂变化。

**旁白**

> Key 被删除后，下一批并发请求几乎同时完成第一次 Redis 查询，它们看到的是同一个结果：MISS。如果没有保护，这些请求会把一次缓存失效放大成多次数据库查询，这才是缓存击穿真正危险的地方。

**为什么下一步这样操作**

接下来需要回答：这些 MISS 为什么没有全部访问 MySQL？

**这一幕证明什么**

并发 MISS 是风险起点，MISS 本身并不是保护方案。

---

### 第八幕：Mutex、双检与 Leader

**时间：** 4:50–5:50

**画面操作**

重点录下因果动画的前半段：

- MISS 波进入 Gate
- `KEY MUTEX`
- `DOUBLE CHECK`
- Leader 二次查询 Redis
- Leader 进入 MySQL

动画过快时不要边录边连续点击，应完整录下并在后期冻结关键帧。

**观众此时看到什么**

请求第一次 Redis MISS 后进入按 Key 的保护模块。其中一个请求继续向 MySQL，其他请求停在等待状态。

**旁白**

> 这里不是 singleflight，页面展示的是按 Key 的 Mutex 加双检。第一次 Redis MISS 之后，请求先竞争这个 Key 对应的回源闸门。第一个获得执行权的请求临时成为 Leader。但它不能拿到锁就直接查询 MySQL，还要再查一次 Redis，因为它排队期间，缓存可能已经被其他请求回填了。只有第二次检查仍然 MISS，Leader 才真正访问 MySQL。

**为什么下一步这样操作**

解释完 Leader 为什么回源，接下来要交代 Followers 到底发生了什么。

**这一幕证明什么**

二次检查避免“已经有人回填完成，后来的请求仍然重复回源”。

---

### 第九幕：Leader 回填，Followers 恢复

**时间：** 5:50–6:40

**画面操作**

录下后半段：

- `Leader SET DTO`
- MySQL → Redis 回填
- Followers 被唤醒
- Followers 二检 Redis HIT
- 响应返回
- Redis Key 恢复存在

**观众此时看到什么**

只有 Leader 经过 MySQL；回填完成后，Followers 从 Redis 返回，MySQL 节点不再继续被访问。

**旁白**

> Leader 从 MySQL 取回结果后，把完整 DTO 写回 Redis。等待中的 Followers 不是共享 Leader 的 HTTP 响应，它们仍然是各自独立的请求。只是轮到它们继续执行时，会再次检查 Redis，这时已经 HIT，所以它们直接返回，不再访问 MySQL。这就是用少量等待换数据库稳定。

**为什么下一步这样操作**

动画已经讲清过程，最后必须用数字证明它确实发生了。

**这一幕证明什么**

回源保护没有消灭请求，而是把多次数据库访问合并成一次重建。

---

### 第十幕：用 15、1、14、16ms、99% 闭环

**时间：** 6:40–7:45

**画面操作**

等待任务完整结束，停在冻结结果：

- 稳定命中
- 失效后 1 秒
- 恢复稳定
- 等待后合并
- 缓存重建
- 失效 → 重建
- 失效 → 稳定
- P95 / 峰值

**观众此时看到什么**

使用当前示例：

- 15 MISS
- 1 MySQL 回源
- 14 等待合并
- 16ms 重建
- 约 99% 命中率

**旁白**

> 现在把这轮因果链用指标闭合。15 个请求第一次访问 Redis 时发生了 MISS，但它们没有变成 15 次数据库查询。只有 1 个 Leader 真正回源，另外 14 个 Followers 在等待后复用了回填结果，所以这里形成了一个守恒关系：15 个 MISS，等于 1 次回源，加 14 个等待合并。

> 这里的 16 毫秒，是从热点 Key 失效到缓存重新建立的空窗时间。它不是 TTL，不只是 SQL 耗时，也不能理解成每个 Follower 都完整等待了 16 毫秒。它表示这一轮从失效到可重新命中的恢复速度。

> 缓存明明失效，为什么“失效后 1 秒”仍然可能有大约 99% 的命中率？因为一秒是统计窗口，而缓存真正缺失的时间只有十几毫秒。这个窗口前面出现了一小批 MISS，后面绝大多数请求已经重新 HIT，所以最终聚合出来仍然是高命中率。不能把“失效后 1 秒”理解成缓存整整不可用了 1 秒。

> P95 和峰值也要一起看。如果受影响的请求不到 5%，P95 可能变化并不大，因为它会被大量正常 HIT 稀释；峰值更容易捕捉这次短暂抖动。恢复稳定后，MISS 和 MySQL 回源重新归零，才算闭环完成。

**为什么下一步这样操作**

有了过程和数字，最后总结设计取舍，而不是继续念更多指标。

**这一幕证明什么**

只有 `MISS = Leader 回源 + Followers 合并`、缓存重建和稳定恢复同时成立，才能证明回源保护真正有效。

---

### 第十一幕：架构与 Trade-off 总结

**时间：** 7:45–8:30

**画面操作**

最后停在完整请求机制图：

```text
Go API → Redis → KEY MUTEX / DOUBLE CHECK → MySQL → Redis
```

同时保留右侧冻结指标。

**观众此时看到什么**

常驻 Gate、Redis、MySQL、回填路径和最终结果处于同一画面。

**旁白**

> 这套 Cache-Aside 的设计重点有三个。第一，正常 HIT 必须足够短，直接从 Redis 返回，不经过锁和 MySQL。第二，MISS 时不能让所有请求一起回源，所以用按 Key 的 Mutex 把同一个热点的重建合并起来。第三，拿到锁后必须双检，避免重复查询数据库。

> 它的代价也很明确：一部分 Followers 会增加等待时间；按 Key 的热点仍然会形成局部竞争；页面标出的 PROCESS-LOCAL 也说明这套保护覆盖的是当前应用进程，不能直接外推成多实例全局保护。所以它解决的是单进程热点重建，不是所有分布式缓存问题。

> 最后我的结论不是“上了 Redis 就一定快”，而是：稳态 HIT 把重复读取移出 MySQL 热路径；缓存失效时，再用可控的短等待，把一波并发 MISS 压缩成一次数据库回源。

**为什么下一步这样操作**

到这里结束，不再进入缓存穿透、MQ 或其他模块，保持主题集中。

**这一幕证明什么**

Cache-Aside 的完整价值是“稳态性能收益 + 失效时数据库保护”，两者缺一不可。

## 五个关键数字的解释口径

| 页面数据 | 正确说法 | 不要这样说 |
|---|---|---|
| 15 MISS | 15 个请求第一次 Redis 查询未命中 | 15 次数据库查询 |
| 1 MySQL 回源 | Leader 二检仍 MISS 后，真正访问一次数据库 | Redis 只处理了一个请求 |
| 14 等待合并 | Followers 等待回填，之后二检 HIT，各自返回 | 14 个请求被丢弃或共用一条 HTTP 响应 |
| 16ms 重建 | Key 从失效到重新可命中的空窗 | 每个请求都等待 16ms，或 SQL 固定耗时 16ms |
| 约 99% 命中率 | 一秒窗口中，十几毫秒后大量请求重新 HIT | 缓存没有真正失效 |

如果页面同时出现“1 次回源”和“多条 SQL”，也不矛盾：回源次数表示一次详情组装请求，SQL 数表示这次组装内部执行的查询数量，录制时不要混成同一个指标。

## 最值得特写的指标

### 稳态对比

- 实际 QPS
- 目标完成率
- 请求 P50 / P95 / P99
- MySQL 查询或回源
- Redis HIT / MISS
- Socket Errors / Error Rate

### 热点击穿

- Redis Key 是否存在
- 失效后 HIT / MISS
- MySQL 回源
- 等待后合并
- 缓存重建次数
- 失效 → 重建
- 失效 → 稳定
- 服务端 P95 / 峰值

不要把稳态最终面板中的请求 P95，与热点卡片中的服务端 P95 混成同一口径。镜头里应保留指标标题。

## 录制表达注意事项

- 3A～3D 因果动画可能很快，建议先试录一轮，正式录制时完整捕捉，后期冻结关键帧。
- 不要在数字仍跳动时念最终结论；等任务完成后使用冻结结果。
- “1 次 MySQL 回源”必须和“15 MISS、14 合并、错误为 0”一起讲，单独一个数字不足以证明保护成功。
- “失效 → 稳定”如果明显长于 16ms，不要说缓存一直不可用到稳定时刻。前者是重建空窗，后者是系统确认重新稳定所需的观察时间。
- 所有数字必须来自同一轮、同一阶段。不要把“当前一秒”“整轮累计”和另一轮实验的数据拼在一起。

## 建议删除的内容

为了避免视频像八股课，这一条视频不要讲：

- 缓存穿透和负缓存
- singleflight
- MQ、Outbox、秒杀库存
- Redis 基础数据结构教学
- Runner 事件日志逐条解读
- 四档 QPS 全部跑一遍
- 所有延迟指标逐项念数
- “Redis 一定比 MySQL 快”这类绝对结论
